## Behaviour
- **Pre-call invariant.** `reserve` inserts a UNIQUE `open` reservation and raises the tenant's held funds in one transaction before any provider I/O; if the cap would be exceeded it writes nothing and returns None (HTTP 402).
- **Exact-once settlement.** `settle` moves `open` to `settled` in one transaction (reservation row, tenant spend and held funds, audit event). A second settlement raises `BudgetStateError` and changes nothing. Unknown or malformed usage is charged at the bound (recorded with a NULL actual); an actual cost above the bound is recorded in full and counted as a breach. These are usage-priced estimates, not provider invoices.
- **Crashes.** A reservation left `open` (the process died after reserving, or after the provider answered but before settling) **stays held** against the cap across any number of restarts. Nothing resets it and nothing re-sends the request. Only `resolve` (named operator + reason) releases it: the default charges the full bound; a smaller `--charge-usd` is an explicit, recorded refund decision.
- **Limits.** The first start inserts the configured limit. A later start with a different configured limit **refuses to start**; `set_limit` is the explicit operator action. Spent and held balances are never overwritten by defaults.
- **Startup verification (fail closed).** Schema version, finite non-negative amounts, held funds equal to the open reservations, spend equal to the booked charges, no unknown states, configured tenants present with the persisted limits. Any mismatch raises `GatewayStartupError`; unresolved reservations are reported (`/readyz`), not hidden.
- **Concurrency.** Writers are serialised by `ModelState.transaction()` (`BEGIN IMMEDIATE` on SQLite; PostgreSQL uses `FOR UPDATE`, unverified here). Two runtimes (two connections) on one database cannot jointly exceed a cap (tested with 24 racing threads).
- **Migration.** Opening an existing state database creates the new tables with `IF NOT EXISTS`, records `schema_version = 1`, and does not touch `model_state` or rollout tables. Opening again is idempotent. There is no automatic import from the earlier file ledger or from process memory (prior in-memory spend was never persisted).

## Operational limits and risks
- Exact-once settlement and the cap hold per database; PostgreSQL behaviour is unverified until it can be run.
- `remaining()` and the other read properties are snapshots; the authoritative check is the transactional `reserve`, so a stale read can only cause an extra 402 or a harmless pre-check pass, never an overspend.
- A runtime whose process dies leaves its reservations held until an operator resolves them; an alert or runbook for `unresolved_budget_reservations > 0` is not provided. Distinguishing a crashed runtime from one still in flight relies on the operator (each row records its runtime `owner` and creation time).
- Settlement failure after a successful provider call returns 503 to the caller although the provider was called and the funds stay held; that is deliberate (fail closed, no retry) and may surprise clients.
- Authentication, streaming and the rollout worker are separate pieces; streaming and the older file ledger keep their own settlement paths (streaming settles through the same `reserve`/`settle` interface, so it inherits durability when the database budgets are used, but that combination was not re-tested end to end here).
- No alerting, key rotation, rate limiting, multi-region or live latency evidence was added.

## Per-reservation validation (added 2026-10-08, after an independently reproduced gap)
**Gap.** `BudgetStore.verify()` checked tenant aggregates only, so a reservation with a negative `amount_usd` passed when the totals still balanced (reproduced in a scratch database, never the real ledger). A second finding from the same pass: a tenant figure stored as the text `'nan'` made the cap comparison false, so `reserve` failed open.

**Fix (`gateway/budget_store.py`).**
- `check_reservation_row` validates each persisted reservation by state: bound finite and non-negative; `open` rows have every terminal field NULL; `settled`/`resolved` rows have a finite non-negative booked charge and settlement time; a known actual equals the booked charge (1e-12); unknown usage (NULL actual) is booked at exactly its bound; the breach flag is an integer equal to (charge > bound); `settled` rows carry no resolution; `resolved` rows carry a JSON resolution with string operator and reason and a boolean charge declaration consistent with the stored actual; unknown states are rejected.
- `verify` checks every reservation, then the aggregates (held funds = sum of open bounds, spend = sum of booked charges, breach count = number of breaching rows), with comparisons written so NaN/inf fail; tenant names must be non-blank strings; orphans are found with `NOT EXISTS` (a NULL tenant row cannot hide them); configured limits must be valid figures.
- `reserve`, `settle` and `resolve` re-validate before any balance changes (`_locked_tenant`): the tenant row and its breach count, every non-terminal reservation of the tenant, and stored held funds against their sum; `_close` also validates the target row and refuses a booking that would make recorded spend non-finite. `ensure_tenant` and `set_limit` refuse to act on malformed books. `unresolved()` and `snapshot()` validate what they report.
- Refusals read "refusing to change balances: ...; nothing was repaired, refunded or discarded". Nothing is repaired, refunded, defaulted or discarded automatically; handling a malformed row is an operator decision outside this code.
- Strict inputs: money arguments reject booleans and numeric strings (`_finite`), huge ints give `BudgetStateError`, caller-supplied clocks and operator/reason/tenant strings are validated.
